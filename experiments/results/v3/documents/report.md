# X3. Реестр документов (D6): метод, ограничения, результаты

Модуль: `src/cashflow_ml/documents.py`. Оценка: `evaluate_documents.py`, таблицы собирает
`make_report.py` (раздел «Результаты» ниже сгенерирован из JSON, числа не правились вручную).

## Метод

1. **Парсер** (`parse_purpose`): вид документа (акт, УПД, накладная, счёт, договор), номер (с «№» и
   без), дата `дд.мм.гггг`, номер договора, стадия платежа (оплата, предоплата, окончательный расчёт,
   частичная, доплата, возврат). Платёжный документ — акт > УПД > накладная > счёт, обязательно с датой.
   Лицевой и расчётный счёт документом не считается; слово «расчёт» тоже (был дефект регулярки, исправлен
   и закрыт тестом). Контрагент — ИНН операции (при нулевом ИНН — имя).
2. **Документы**: ключ (компания, направление, контрагент, вид, номер, дата). Частичные оплаты и доплаты
   одного документа объединяются в один документ с несколькими платежами. В реестр идут категории
   `customer_payment` (поступления) и `supplier`, `contractor`, `logistics` (списания). Регулярные
   счета (аренда, коммунальные, связь, ПО, охрана, бухгалтерия) оставлены механизмам X2.
3. **Срез на as_of** (`DocumentUniverse.registry`): документ с датой ≤ as_of и платежами после as_of.
   Сумма события = сумма платежей после as_of (D6). Ожидаемая дата = дата документа + медиана задержки,
   перенос на следующий рабочий день по `calendar_ru`, не раньше as_of + 1 рабочий день. Фактическая
   дата будущих платежей в дату события не попадает (тест `test_future_payments_do_not_leak_into_expected_date`).
4. **Задержка** оценивается только по документам, полностью оплаченным до as_of: уровни клиент
   (в рамках компании, мин. 5 наблюдений) → отрасль (мин. 20) → все (мин. 20) → запасной вариант
   as_of + 7 дней. Выборка условна на «не оплачен к as_of» (берутся задержки ≥ возраст документа).
   Квантили q10/q25/q50/q75/q90 сохраняются в событии (`delay_quantiles`, `window`) для X6.
   Параметры (охранный возраст, условность, минимум клиента) выбраны на калибровочных срезах
   2026-01-01…01-29, срезы выбора и ретро для подбора не использовались.
5. **Договоры**: предоплата по договору № X (стадия prepayment) в паре с окончательным расчётом по
   тому же (компания, направление, контрагент, номер) — i-я предоплата с i-м расчётом по порядку дат.
   Событие «окончательный расчёт» (`contract_settlement`, `known_at` = дата предоплаты): сумма =
   предоплата × медианное отношение расчёт/предоплата по истории (клиент → отрасль → все), дата =
   предоплата + лаг по истории (та же иерархия и условность).

## Смещение выживаемости (явно)

В выписке есть только оплаченные документы. Выставленный, но не оплаченный до конца архива
(2026-09-30) документ в реестр не попадает; также в реестре есть только те документы, у которых
оплата случилась после as_of в пределах архива. Следствия:
- реестр оптимистичен: среди открытых документов нет безнадёжных долгов, а факт «документ будет
  оплачен» известен модели из будущего. Доля покрытия «потолок» в таблицах завышена на неизвестную
  величину по сравнению с живым реестром 1С;
- модель задержки по построению не видит неоплаченных документов, поэтому хвост задержек занижен;
- для контрактов существование окончательного расчёта тоже известно из будущего (циклы без расчёта в
  архиве в реестр не входят);
- для последних срезов ретро документы, оплаченные после 2026-09-30, невидимы (правое усечение);
- чувствительность «клиент не заплатит» (сценарий D6) здесь не считалась: она относится к X9.

## Что принадлежит реестру (для X4: без двойного счёта)

Реестру принадлежат будущие операции (дата > as_of), которые: (а) оплачивают документ с датой ≤ as_of
в категориях `customer_payment` (вх.), `supplier`, `contractor`, `logistics` (исх.), либо (б) являются
окончательным расчётом по договору, предоплата по которому ≤ as_of. Программно:
`DocumentUniverse.owned_payments(account_id, as_of)` (только для оценки, использует будущее) и
`owned_categories()`.

Правило для X4: на категориях `customer_payment`, `contract_settlement` (вх.) и `supplier`,
`contractor`, `logistics` (исх.) события реестра заменяют структурный или ML-прогноз на сумму
открытых документов; прогноз другого источника по этим категориям оставлять только как остаток —
оплаты документов, которые ещё не выставлены на as_of (в таблицах это разница между потоком
категории и потолком). Эквайринг, СБП, наличные, маркетплейс, зарплата, налоги, аренда и другие
регулярные потоки реестру не принадлежат. Нельзя складывать реестр с моделью «счета клиентов» из
`mechanisms` для тех же контрагентов без вычитания перекрытия.

## Оговорки

- Данные синтетические. Уровень «клиент» заметно точнее «все» (раздел 4); на реальных выписках
  этот выигрыш не проверялся и может быть меньше.
- Окна не независимы: недельные срезы, документ учитывается на каждом срезе, пока открыт.
- «Потолок» не является прогнозом: это доля потока, которую реестр мог бы покрыть при точном
  знании дат. Ожидаемая и фактическая оплата в окне (попадание) — достижимая оценка.
- Сумма окончательного расчёта по договору плохо предсказывается медианным отношением: доля
  предоплаты (≈30%, 40%, 50%) у разных договоров разная и в истории клиента не определяется.
